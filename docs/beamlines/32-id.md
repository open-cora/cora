# 32-ID

*An undulator beamline at the Advanced Photon Source running four
instruments, two of which this register describes: micro-tomography and the
transmission X-ray microscope. It is the second beamline this system
describes. A conductor and a reporter run here against a simulator, and the
whole chain from dispatch to a described file has been walked.*

A beamline descriptor is what a running keeper has to be told about the
beamline it serves, written down where it can be read and reviewed. The rule
that keeps it short, and what that rule costs, is in
[`beamlines/README.md`](https://github.com/open-cora/cora/blob/main/beamlines/README.md).
The unit here is the beamline and not the instrument: 32-ID's instruments
share a front end, an insertion device and a monochromator, and a claim
ledger belongs to a conductor, so modelling two instruments apart would
leave nothing between two walks and the shared optics.

## The device register

[`beamlines/32-id/devices.toml`](https://github.com/open-cora/cora/blob/main/beamlines/32-id/devices.toml)
holds 38 devices across two instruments: 13 at the micro-tomography
station and 25 at the transmission X-ray microscope. All 38 are
confirmed against the beamline, but not all to the same standard, and the
file keeps the difference rather than flattening it.

**The instrument lives in the device name**, which is the partition this tree
settled on rather than a field no keeper command accepts. A name beginning
`TXM` is the microscope; an unprefixed name is the micro-tomography station.
That asymmetry is deliberate and the register says why: a device's name is
fixed when it is registered, the keeper has no rename, and the seeding
script keys on the reference alone, so renaming the five older rows here
would make the file disagree with the record and nothing could reconcile
them.

### The micro-tomography rows

**Three of them rest on better evidence than the other two**, and the file
keeps the difference rather than flattening it. The acquisition software is
configured over Channel Access, so its own settings are records whose values
are the names of other records. Asking it what it drives is therefore record
to record with nothing translated between one system's model and another's,
and it answers with a role rather than a position in a crate:

```
RotationPVName  ->  32idcSoft:ens:c1:m1
SampleXPVName   ->  32idc02:m39
SampleYPVName   ->  32idc02:m23
```

The other two are an alignment pitch and roll. The software does not drive
them, so what the sweep checked is that each record exists and answers.
Their names were authored from the beamline's own manual, like every other
name here and unlike the facility's description field, which says how a
stage is wired rather than what it is for. The facility's own page for this
instrument has since given both the same roles this register gives them, so
those two names are corroborated where the other three are derived. That is
a weaker kind of support and worth keeping distinct, which is why the file
says which is which.

### The TXM rows

The microscope has its own scan server, its own optics server and its own
sample stack. It is a separate instrument rather than another name for the
same one, and upstream tomoscan carries a class for each, the micro-CT one
describing itself as architecturally closer to 2-BM than to the microscope
next door.

A read-only sweep of its motor IOC reached each of the four records, and
each answered with a role:

```
32idbTXM:ens:c1:m1          Rotation
32idbTXM:mcs:c2:m1          Sample Top X
32idbTXM:mcs:c2:m2          Sample Top Z
32idbTXM:uniblitz:control   answers, reads Close
```

**It is the weaker standard, because that instrument's scan server is
down.** The microscope's TomoScan serves its bindings as records, so the
record to record question could have been asked of it. The sibling station
answered the same question in the same minute; this one did not answer at
all. So these names are roles the hardware gave, not bindings a server
confirmed, and nothing here says which record a scan would actually drive.

**There are two sample top pairs, and the register holds the older one.** A
second controller answers as Sample Top X(new) and Sample Top Z(new),
holding a different position from the pair above, and the scan server's
configuration names the older pair. Which one carries the sample today is
a question for the beamline, and it should be answered before anything
drives either.

An earlier version of these rows was authored from the scan server's
configuration file instead, and called the second record a sample Y. The
hardware calls it Z. That file names the pair under both spellings, and
reading the first is how an axis changed letter on the way in. Checking
that file against the two beamlines where this system had asked the running
server is what prompted the sweep: it disagreed with both, at 7-BM naming a
pair whose driver was commented out in March 2026, leaving records with no
motor behind them.

**The optics are rows now, and finding them took a second controller.**
Zone plate, condenser, pinhole, diffuser, beamstop, beam position monitor,
scintillator and the camera rotation are driven through an optics server
rather than by the scan engine, so neither the scan server's configuration
nor any facility page names them: those pages give focal distances and
colour-coded mount positions and not one record name across ten of them.
They sit on a second SmarAct controller that no page mentions, so probing
the first returned nothing and read exactly like an instrument with no
optics. Reading the IOC's own record dump is what found them, and each then
answered with its role.

**Five records answered and are deliberately absent**, on the rule 19-BM's
register states: a row whose name would have to be invented is the guessing
this directory exists to avoid. One calls itself not connected and two name
a controller and a channel rather than a thing. The other two are a phase
ring pair that carries the same label twice, so they are plainly two
mechanisms and only one of them could be named without guessing. That is a
defect in the beamline's configuration worth reporting rather than a reason
to invent a name here.

**The detector is deliberately not a row.** Asked for its camera, the
software answers with a bare prefix, ending in a namespace separator and
naming no record, and the file plugin it writes through answers the same
way. A reference here is one record and never a namespace, so there is no
honest way to write either of them down. That is not a defect in the
software, which is describing an interface that really is a namespace of
many records. It is this register modelling one of the two shapes the rest
of the tree already tells apart.

The count is pinned in `beamlines/tests/`, which discovers registers by glob
rather than naming one, so a beamline directory added without a pin fails
rather than going unchecked.

## Which host can see the hardware

**The two workstations have opposite properties, and neither has both halves
of what a client needs.**

| | the routable host | the private one |
| --- | --- | --- |
| Network | routable | beamline private |
| Reaches the internet | yes | no |
| Finds IOCs by broadcast | no | yes |

That was measured rather than assumed, and the first survey attempt from
the routable host found nothing at all, which read as it being disqualified.
It is not. That host routes to the private subnet in under a millisecond, and
with an explicit Channel Access address list every record above answers. So
a conductor can run there, and it is the better of the two, because
installing software on the private one would mean carrying it across the boundary
the way 2-BM has to.

**A conductor at 32-ID therefore needs its Channel Access address list set
explicitly.** Nothing in the descriptor carries that. It is a fact about a
host rather than about the beamline, and the process that needs it reads it
from its environment.

The micro-tomography IOCs sit on three hosts rather than on either
workstation: the sample stack on a motor IOC of its own, the rotation stage
on a soft IOC of its own, and the scan server and the camera on the private
workstation. The microscope's IOCs are a separate set on a workstation of
their own, with one more for its condenser shaker, and none of them has been
reached from here.

## What is not configured yet

A conductor and a reporter run on the routable host, and two simulators on a
private one. The
reporter reads TomoScan's records rather than a document stream, which is
what removed the barrier this section used to describe: TomoScan publishes
no documents at all, which `spikes/tomoscan_adapter/FINDINGS.md` measured at
2-BM and which nothing seen here contradicts.

| | where | what it is pointed at |
| --- | --- | --- |
| conductor | the routable host | `corasim32id:` to write, `corasim32id:TomoScan:` to run |
| reporter | the routable host | the records at `corasim32id:TomoScan:` |
| simulated motors | a private host | `corasim32id:` on port 5065 |
| simulated TomoScan | a private host | `corasim32id:TomoScan:` on port 5066 |

**Neither simulator stands for either instrument.** The motors are caproto's
fake motor record under generic names, and the TomoScan server is faithful
to the record names and types measured at 2-BM. What they prove is that a
conductor can reach a record, set it and walk a procedure, which is a fact
about the seams rather than about 32-ID's hardware.

**The microscope is registered and not driven.** Its scan server is a second
TomoScan at a prefix of its own, and a conductor holds exactly one: `[run]`
in its configuration names a single prefix, and one conductor per beamline
is the decision a shared insertion device and monochromator force, because
two conductors would mean two claim ledgers with nothing between them. So
driving the microscope is not a configuration change, and registering its
devices does not make it reachable. Its records are also absent from the
conductor's writable list on purpose, which is what keeps a deployment
writing only to records this system serves.

**The ports are not a preference here, and this is the beamline that shows
why.** The routable host finds nothing by broadcast, so every record it reads is
reached by an explicit address naming a host and a port. Two simulators on
one host cannot both have the default, so each is given one and the
conductor's list names both. Everywhere else the same arrangement is a
tidiness; here it is the only thing that works.

**Discovery is not symmetric, which the install found the hard way.** From
the simulator host the beamline answers by broadcast and does not answer a
unicast addressed to that host itself, so a simulator installer run there with an
explicit list refuses before it starts, reporting that it cannot see the
beamline. From the routable host the reverse holds. Neither host is wrong and
neither view is the beamline's; what each proves is what that host can
reach.

That spike also records 32-ID as the one tomography station with a pause
record where 2-BM has none. The survey did not find one: the record it names
does not answer on the instrument surveyed here. The spike was reading an
upstream template rather than a running system, so the narrow reading is
that this instrument does not serve that record, not that the template lacks
it.
